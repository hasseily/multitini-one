# C64 disk launch firmware 20260916

## Board report with candidate 20260915

The user reports that things generally work, but Ultima II behaves differently
depending on how it is loaded. Manual `LOAD"*",8,1` then RUN, and manual
`LOAD"ULTIMA II",8,1` then RUN, reach the second-disk prompt. The menu's Right
shortcut followed by manual RUN also reaches that prompt. Mount & Run with
Enter loads ULTIMA II but later reports a disk read error. Selecting ULTIMA
instead returns to BASIC.

The inspected local disk confirms that ULTIMA II is its first closed PRG and
contains a BASIC SYS entry at `$0801`. ULTIMA is a later module loading at
`$2000`, called by the startup program. Loading that module alone does not
establish a BASIC start point.

The working native path isolates the board failure to the direct launch
shortcut. The precise missing state is not established. In particular, setting
the remembered drive number alone is not a proven fix: the CPU/1541 model
reaches the later disk prompt even with the old direct-loading sequence.

## Generic behavior change

Enter now launches a valid BASIC disk program through the actual C64/1541
LOAD path. Firmware builds a small original BASIC program:

```basic
10 LOAD"<exact selected name>",8,1
```

It stages this launcher, restores the disk, then starts the launcher. The
original BASIC ROM starts the newly loaded BASIC program after a successful
in-program LOAD. Firmware does not guess a delay or queue a second RUN after
an error. This preserves the real KERNAL and drive loading side effects.

In-program LOAD retains BASIC's variable start pointer. The staged launcher
therefore reserves at least the target PRG's entire memory extent, using zero
padding after its BASIC end marker. Without that reservation, a larger loaded
BASIC program can overwrite itself when it creates variables. Large and short
variable-program regressions cover this. For a target shorter than the launcher,
variables begin after the launcher extent, leaving a small unused gap.

- Enter: drive LOAD and automatic BASIC startup. Non-BASIC entries receive
  direct-mode LOAD and retain their own startup behavior.
- Right: drive LOAD only, followed by manual RUN when appropriate.
- Left: the previous direct RAM load and RUN, for valid BASIC programs only.
  This is faster but can fail with programs that need normal disk-load state.
- `[load only]` marks entries without a validated BASIC start. They may be
  bootstraps or later modules; their machine-code entry points are not guessed.

The rules inspect PRG structure and exact filenames. There are no game-name,
disk-name, or disk-hash exceptions. Ambiguous or untypeable native names are
refused before reset/eject; Left remains available for valid BASIC entries.

## Validation and build

Original synthetic tests exercise real stock-ROM loading, automatic startup,
a subsequent disk LOAD using the saved device, and a missing-file error that
returns to BASIC without retrying. C tests verify launcher bytes, names,
capacity handling, failure atomicity, and menu shortcuts.

On the private Ultima II image, the launcher performs one exact native LOAD,
reaches SYS2061 with the full PRG matching the disk, and continues through the
intro and its later ULTIMA module LOAD to `INSERT PLAYER DISK AND PRESS <F1>`.
There is no injected second RUN or disk write. The manual native comparison
reaches the same prompt. This is CPU/1541 simulation evidence, not a new board
test or video/gameplay qualification.

Strict firmware host tests passed 28/28, as did the ASan/UBSan run. The Python
suite completed 139 tests with 3 skips and no failures. A separate original
program verified automatic startup with the existing fast ROM pair and no
disk writes. The unchanged HDL retains its 20260915 build/test evidence.

Firmware `20260916` uses the verified supervisor FPGA and FSBL from
`20260915`, with its software platform rebuilt from the same supervisor XSA
in `build/v16c`. No HDL changes were needed. Keep the C64 package from `20260915`
and the existing GBC package. Firmware and FPGA build numbers intentionally
differ for this firmware-only update; ABI remains 0.10.

The firmware output is `build/firmware-20260916/FIRMWARE.BIN`.
Build, test, input-provenance, and payload-audit records are under
`build/validation20260916`. No SD card or board was modified during this work.

## Board retest

1. Update only FIRMWARE.BIN. Verify the UART firmware version is 20260916;
   active C64 shell build remains 20260915, ABI 0.10.
2. Start with the same ROM/turbo settings used for the working manual test.
   Select ULTIMA II with Enter, then close F12 and wait for the disk load.
   No manual LOAD or RUN is required. Continue to the player-disk prompt.
3. Retest Decathlon and Colors with Enter, and the Ultima I bootstrap.
4. Right remains the manual LOAD comparison; Left reproduces the old direct
   launch path. Capture the full launch log and `s` / `:disk` if Enter fails.

The next board report shows `READY.`, `RUN`, then
`?FILE NOT FOUND ERROR IN 10`, returning to BASIC. This is a failure in the
launcher's LOAD before the target program starts. The user then confirmed
LIST shows `10 LOAD"ULTIMA II",8,1`. Another RUN fails, as do manual
LOAD commands for ULTIMA II, `*`, and `$` without resetting or remounting.
The previously confirmed workaround is Right to LOAD, then manual RUN.

Follow-up checks have not reproduced this failure under the normal launch
sequence. Actual C-generated ULTIMA II launcher bytes pass through the real
HDL content loader with all 16,089 staged RAM bytes, BASIC pointers, and RUN
request verified (`build/validation20260917`). Immediate disk insertion and
HDL-equivalent write-protect behavior also pass in the CPU/1541 model. A
conservative 80 ms disk-service blackout after RUN starts passes; a 3-second
blackout can reproduce the reported error. This establishes a possible
failure mechanism, not evidence that the board experiences that delay.
The follow-up source audit found that starting the staged program clears a
shared error flag after remount, canceling a healthy media request. See
[firmware 20260917](C64_LAUNCH_20260917.md) for the correction and validation.
