This does not prove the writable SD copy matches the archive or qualify

The game's SUBS load wrapper calls KERNAL LOAD at `$4B45` and branches on
carry at `$4B48` to the common `LOAD ERROR!`/retry message. Its SAVE wrapper
also uses that message: KERNAL SAVE at `$4BAB`, carry branch at `$4BAE`.
The displayed text therefore does not distinguish LOAD from SAVE failure;
it is not a map checksum check. Runtime callers load MAP/MON/MOB files and
save MOB/MON state, so a gate transition can fail while saving the map being
left. The SAVE path first sends DOS `S0:<filename>` to scratch the old file,
then writes its replacement. A failed replacement could leave a missing
MON/MOB file and cause the later startup failure; this is not yet verified
against the current SD copy. Normal HDL cache reuse, dirty-track write/reload, and disk
generation swaps pass byte-exact diagnostics. The actual SD copy and physical
write-persistence latency remain unmeasured. Metadata and generated
diagnostics are in `build/validation20260918`; no new firmware candidate or
production-code change was made for this follow-up.

## Cause and change

The staged-RUN service cleared `MT_ERROR_CORE_LOAD` after Drive 8 was
remounted. This register write also pulses the disk track service's
`clear_error`, which cancels a healthy pending track read. The ARM-facing
request mailbox still holds the old request while the core creates a new
request. Track stream bytes carry no request ID, so an old request's data
can fill the new receiver. The old completion is ignored, and the next
stream then faults the already-filled receiver. Repeated C64 LOAD commands
cannot repair this ARM/FPGA media-service disagreement.

Firmware 20260917 preserves the mounted drive's state when starting the
staged program. It checks for an existing load error and refuses RUN if one
is present; it does not clear that error or discard the staged program.
Error clearing before the initial stage remains in the reset/eject flow.
There are no disk-name or game-name exceptions.

## Validation

All 28 strict firmware host tests pass, including compilation of the Xilinx
main application. The new pending-request regression fails with the old
RUN-time error clear and passes with the correction. A separate regression
checks that an existing fault is returned without any writes or RUN command.
The focused content-service test also passes ASan and UBSan. Build-input
checks pass: 26 tests, with one environment-dependent skip.

The standalone HDL diagnostic uses the production D64 track service and
asynchronous mailbox, with request publication logic copied from the board
top. It reproduces stale-ID replay and persistent busy/error state with the
old clear sequence. Omitting the clear preserves the request and completes
with a valid buffer, no error, and an idle disk. It uses original synthetic
track data; it does not execute the ARM or 1541 CPUs. Evidence and exact
commands are in `build/validation20260917/D64_CLEAR_REQUEST_DIAGNOSTIC.md`.

The fresh Vitis platform/application build in `build/v17` passes. The
package uses the verified 20260915 supervisor XSA, FPGA bitstream, and FSBL;
all 480 firmware/tool inputs and 134 vendor inputs match their recorded

## Board test procedure

1. Flash `build/firmware-20260917/FIRMWARE.BIN`.
   Confirm firmware 20260917 in the UART boot log. Keep the 20260915 C64
   package and existing GBC package; the FPGA build remains 20260915.
2. With the same ROM and turbo settings as the working manual comparison,
   select ULTIMA II with Enter in Mount & Run, then close F12.
3. Confirm it loads automatically and reaches the second-disk prompt.
4. Repeat the launch from F12 to check reset/remount consistency. Retest
   Decathlon and Colors with Enter afterward.

If it fails, record the UART launch log and `:disk` status before resetting.
The agent did not modify the SD card or flash the board. The successful
physical test was reported by the user.
